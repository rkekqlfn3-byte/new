## 1. 이 계획서가 말하는 “Goal 달성”

JARVIS의 장기 North Star는 끝없이 확장될 수 있으므로, 완료 판정을 두 층으로
나눈다.

### 1.1 Prototype Goal 수용 완료

다음 조건을 모두 만족하면 현재 Prototype Goal을 `accepted`로 판정한다.

1. 사용자의 자연어를 구조화된 행동 또는 안전한 안내로 변환한다.
2. 현재 앱·문서·선택·직전 작업을 실행 직전에 다시 확인한다.
3. 네이티브 앱 쓰기는 미리보기·승인·실행·read-back·Undo 계약을 지킨다.
4. 검증된 성공과 반복 교정만 별도 승인 후 로컬에서 재사용한다.
5. Excel→Word·한글·PowerPoint 업무를 단계별로 실행·검증·재개한다.
6. 실패를 재탐색 가능·사용자 정보 필요·미구현·버그·환경·취향으로 구분한다.
7. 비숙련자가 개발 로그 없이 진행 상황, 결과, 다음 행동을 이해한다.
8. 자동 게이트 8축, 한컴 환경 증거, 수동 수용 3항목이 모두 통과한다.

### 1.2 수용 이후 North Star 확장

사용자 정의 임의 앱 조합, 자유로운 단계 조립, 장기 대화 문맥, 더 많은 Office
작업, 앱 재실행이 필요한 복구, 음성 중심 UI는 Prototype 수용 이후의 다음 제품
주기다. 이 항목을 현재 완료 조건에 무제한으로 넣어 Goal을 영원히 끝나지 않게
만들지 않는다.

## 4. 실행 Phase

### Phase 0 — 기준선 고정

목적: 새 작업 때문에 기존 안전 계약이 흐려지지 않도록 출발점을 고정한다.

작업:

- 현재 HEAD·브랜치·Python·의존성·Windows 앱 환경을 기록한다.
- 전체 회귀와 제품 Goal 게이트를 한 번 실행한다.
- 생성 보고서에 commit과 `dirty=false`가 기록되는지 확인한다.
- 사용자 데이터 경로와 probe 임시 경로가 분리됐는지 확인한다.

완료 조건:

- 자동 회귀 실패·오류 0.
- 기존 Goal 판정이 예상대로 7축 passed + 한글 환경 차단이다.
- 기준선 이후 변경은 작은 기능 단위 커밋으로 분리한다.

예상 작업량: 0.5일.

### Phase 1 — 사용자용 실행 이벤트와 자연어 설명

목적: 비숙련자가 터미널 원문을 읽지 않아도 현재 상태를 이해하게 한다.

구현:

- 기존 `execution_controller.event`, 확인 payload, 실행·검증 결과를 소비하는
  `engine/user_feedback/` 정규화 계층을 만든다.
- `request_received`, `intent_resolved`, `clarification_required`,
  `action_started`, `action_completed`, `verification_passed/failed`,
  `rollback_*`, `action_failed/cancelled`를 표준 이벤트로 만든다.
- API 없이 로컬 한국어 템플릿으로 “무엇을 하는 중인지 → 무엇이 바뀌었는지 →
  검증됐는지 → 다음에 무엇을 하면 되는지”를 표시한다.
- 기본 “작업 내역”과 접을 수 있는 “상세 로그”를 분리한다.
- 영구 진단 이벤트에는 문서 내용·전체 경로·사용자 원문을 저장하지 않는다.

완료 조건:

- 기존 로그가 삭제되거나 손실되지 않는다.
- `verified=false`를 성공으로 표현하지 않는다.
- `undo_available=false`일 때 되돌릴 수 있다고 표현하지 않는다.
- API가 없거나 실패해도 기본 안내가 동작한다.
- 키보드와 ARIA log에서 새 진행 메시지를 읽을 수 있다.

예상 작업량: 2.5~3일.

### Phase 2 — 구조화된 되물어보기

목적: 모호한 명령을 추측 실행하지 않고 사용자가 짧게 보완할 수 있게 한다.

구현:

- 승인 질문(`confirmation_required`)과 정보 보완 질문
  (`clarification_required`)을 분리한다.
- `missing_target`, `missing_range`, `missing_destination`, `missing_sort_key`,
  `missing_filter_condition`, `multiple_possible_intents`,
  `ambiguous_reference`, `multiple_documents`, `multiple_sheets`,
  `context_mismatch`, `unsafe_default` 사유 코드를 고정한다.
- 기존 확인 카드를 재사용하고 추천 선택지는 기본 포커스로 둔다.
- 추천값은 승인 미리보기에 채울 뿐, 쓰기 승인을 생략하지 않는다.
- 같은 선택 3회 후에도 별도 승인 전에는 기본값으로 확정하지 않는다.

우선 적용 순서:

1. Excel 합계·평균의 대상 범위와 결과 위치.
2. 필터 조건과 정렬 기준.
3. 여러 문서·시트·최근 산출물 후보.
4. Word·한글 Range와 PowerPoint Shape 대상.

완료 조건:

- 모호한 테스트 문장의 임의 실행 0건.
- 질문과 위험 승인 카드가 세션·요청 ID별로 격리된다.
- 문맥이 바뀐 오래된 응답은 실행 전에 폐기된다.
- 기존 명확한 명령의 성공률과 속도에 유의미한 회귀가 없다.

예상 작업량: 2~3일.

### Phase 3 — Undo UI 연결

목적: 이미 구현된 4개 앱 Undo를 사용자가 쉽게 발견하고 한 번 안전하게 쓰게 한다.

구현:

- `undo_available=true`인 검증 성공 결과에만 “방금 작업 되돌리기”를 노출한다.
- 문서·세션·대상·현재 지문·직전 작업 ID·Undo 사용 여부를 다시 검사한다.
- 문서 변경, 세션 전환, 앱 종료, 다른 편집 성공, 시간 만료, 이미 사용한 Undo,
  복구 뒤 지문 불일치 시 버튼을 만료한다.
- Undo 후 원래 값·서식·선택이 복구됐는지 read-back한다.

완료 조건:

- Excel·한글·Word·PowerPoint 각각 성공 1회, 만료 1회, 중복 사용 차단 1회.
- 실패한 Undo가 성공으로 표시되지 않는다.
- 키보드만으로 버튼 실행과 결과 확인이 가능하다.

예상 작업량: 1~1.5일.

### Phase 4 — Excel 안정화와 최소 신규 기능

목적: 기능 수보다 실제 사용 빈도와 안전성을 우선해 Excel을 동결 가능한 상태로
만든다.

#### A군: 기존 기능 안정화 — 필수

- 값·수식·합계·평균 입력.
- 굵기·크기·정렬·배경색·글자색.
- 필터·정렬·치환·행/열 삽입·선택 읽기.
- VBA 조회·수정·복원·실행.
- 관계 후보·조인·Word/한글/PPT 워크플로.

각 기능은 대상 명확성, 미리보기, 승인, read-back, 구조화 결과, 자연어 설명,
가능한 Undo, 실패 분류, 해결 안내, 반복 안정성의 10개 조건을 만족해야 한다.

#### B군: 최소 신규 — 여유가 있을 때만

1. 중복 제거.
2. 행·열 삭제.
3. 시트 생성·이름 변경.
4. 열 너비·행 높이 조정.

B군 때문에 A군 안정화나 Goal 수용이 늦어지면 B군을 다음 주기로 이월한다.
차트·조건부 서식·피벗 확장·시트 이동 등은 이번 완료 조건에서 제외한다.

완료 조건:

- A군 전 기능이 동일한 설명·승인·검증·Undo 정책을 사용한다.
- 기존 100문장 수동 시험에서 중대 오대상·무승인 쓰기 0건.
- 실앱 반복 probe가 사용자 문서·프로세스를 건드리지 않는다.

예상 작업량: A군 2일, B군 선택 시 추가 2~4일.

### Phase 5 — 1,000문장과 실앱 수용 배터리

목적: 개발자가 생각한 표현이 아니라 실제 사용자의 말에서 실패를 찾는다.

문장 배분:

| 유형 | 수량 |
|---|---:|
| 직접 명령 | 400 |
| 정보가 빠진 명령 | 200 |
| 문맥·직전 참조 | 150 |
| 오타·붙여쓰기·구어체 | 100 |
| 복합 요청 | 100 |
| 위험·승인·Undo | 50 |

평가 결과:

- `correct_action`: 올바른 구조화 행동.
- `correct_clarification`: 필요한 정보만 질문.
- `safe_block`: 미지원·위험을 정확히 차단.
- `wrong_action`: 잘못된 행동 또는 대상.
- `crash`: 예외로 종료.

합격 기준:

- crash 0.
- 무승인 쓰기 0.
- 위험 명령 안전 차단 100%.
- 잘못된 앱·문서·범위 실행 0.
- 직접 명령 구조화 성공 95% 이상.
- 불완전 명령의 올바른 질문/차단 95% 이상.
- 같은 문장을 반복해도 API 호출이 불필요하게 증가하지 않는다.

인프라:

- 해석 계층은 임시 `JARVIS_DATA_DIR`와 mock 실행기로 격리한다.
- 실행 계층은 JARVIS 소유 임시 문서와 기존 probe를 사용한다.
- 실패 문장에는 원문 대신 케이스 ID·분류·사유 코드를 영구 기록한다.

예상 작업량: 자동 배터리 1.5일, 실제 사용자 재시험 1~2일.

### Phase 6 — 한글·VBA 환경 증거 해소

이 Phase는 사용자의 명시적 환경 조치가 필요하다. JARVIS가 자동으로 보안 설정을
바꾸지 않는다.

한글:

1. 한컴 공식 Automation 가이드의 파일 접근 보안 모듈을 사용자가 설치·등록한다.
2. JARVIS는 등록 이름·파일 존재를 읽기 전용으로 검사한다.
3. HWP 생성 probe와 Word+HWP 동시 workflow probe를 새로 실행한다.
4. 내용·서식 read-back, 부분 파일 부재, 원본 불변, 소유 프로세스 정리를 확인한다.

Excel VBA:

1. 실제 VBA 수정·실행까지 수용하려면 사용자가 Excel 보안 센터의 “VBA 프로젝트
   개체 모델에 안전하게 액세스” 허용 여부를 직접 결정한다.
2. 허용하지 않으면 기능은 `environment_blocked`로 남기고 제품이 우회하지 않는다.

완료 조건:

- `workflow_hwp`가 `passed`로 갱신되거나, 사용자가 해당 기능을 Prototype 수용
  범위에서 명시적으로 제외한다.
- 자동 설치·다운로드·레지스트리 우회 기록이 없다.

예상 작업량: 환경 준비 시간 별도, probe 0.5일.

### Phase 7 — 수동 수용 3종

#### 7.1 실제 화면 읽기 프로그램

- NVDA 등으로 명령 입력, 모드 전환, 확인 카드, 오류, 완료, Undo 흐름을 수행한다.
- 읽는 순서, 중복 낭독, 포커스 손실, 버튼 이름을 기록한다.

#### 7.2 실제 음성 입력

- 날짜·날씨·앱 열기·Excel 편집·확인 응답·Undo 대표 문장을 수행한다.
- 잘못 인식한 문장은 자동 실행하지 않고 수정·재질문할 수 있어야 한다.

#### 7.3 비숙련 사용자 관찰

- 대표 20문장을 도움 없이 먼저 수행하고, 막힌 항목만 100문장으로 확장한다.
- 측정값: 첫 성공 시간, 질문 횟수, 잘못된 실행, 도움 요청, 포커스 혼란,
  오류 안내 이해 여부.
- 한 명의 결과로 일반화하지 않고 반복 문제만 코드·문구 수정 후보로 만든다.

완료 조건:

- 세 항목의 실제 수행 시각과 `passed`만 수동 증거 JSON에 기록한다.
- 사용자 메모·원문·문서 내용은 Git에 넣지 않는다.
- 발견 결함은 수정→관련 회귀→해당 수동 시나리오 재시험까지 끝낸다.

예상 작업량: 1~3일이며 사용자 일정에 의존한다.

### Phase 8 — 최종 clean 수용 게이트

순서:

1. CRLF·문서·버전·테스트 등록 정합성 검사.
2. 전체 자동 회귀.
3. 관련 Stage 5~12 실제 probe 갱신.
4. 수동 증거 연결.
5. 제품 Goal 게이트 실행.
6. 실패 0, `overall_status=accepted`, commit 고정.
7. `Prototype Goal accepted` 태그와 `git archive` 소스 백업.
8. 원격 `main`, 개발 브랜치, 태그를 교차 확인한다.

완료 조건:

- 전체 회귀 실패·오류 0.
- 모든 필수 probe가 7일 이내이며 사용자 문서 변경 0.
- `source.dirty=false`이고 보고서 commit이 태그 commit과 같다.
- `overall_status=accepted`와 CLI 종료 코드 0.
- Python 소스 실행 기준 완료. EXE·배포·서명은 별도 사용자 지시 전까지 하지 않는다.

예상 작업량: 1일.

## 5. 총 일정과 병렬화

코드 기준 기본 작업량은 **10.5~13일**, 선택 B군까지 포함하면 **12.5~17일**이다.
날짜 약속보다 각 Phase의 완료 증거를 우선한다.

권장 순서:

→ Phase 2 되물어보기

`accepted` 판정은 두 Phase가 끝난 뒤에만 가능하다.

## 6. 우선순위와 중단 기준

### P0 — 즉시 막아야 하는 것

- 승인 없는 쓰기·삭제·덮어쓰기.
- 다른 문서·시트·선택 대상 실행.
- 검증 실패를 성공으로 표시.
- Undo 가능 여부의 거짓 표시.
- 사용자 문서 내용·경로·API 키의 로그·Git 유출.

P0 발견 시 신규 기능 작업을 중단하고 원인 재현·수정·전체 관련 회귀를 먼저 한다.

### P1 — Prototype 완료에 필요한 것

- 진행 설명, 되물어보기, Undo UI.
- 기존 Excel 기능의 UX 계약 통일.
- 1,000문장과 실제 앱 증거.
- 한글 환경과 수동 수용 3종.

### P2 — 수용 후 확장

- 사용자가 허용 단계를 조합하는 범용 레시피 편집기.
- 임의 앱 조합과 사용자 정의 후조건.
- 장기 대화 문맥과 더 긴 지시 대상 연결.
- 앱 자동 재실행이 필요한 복구·보상 트랜잭션.
- 음성 중심 UI, 새 Office 기능, 대규모 UI 개편.

## 7. 변경·검증 운영 규칙

- 한 번에 한 Phase만 `in_progress`로 둔다.
- 기능·테스트·문서를 같은 작은 커밋에 넣는다.
- 테스트 모듈 추가 시 `tests/test_runner.py`도 같은 커밋에서 갱신한다.
- 사용자 문서·실행 중 Office 프로세스·사용자 데이터 저장소를 probe에 쓰지 않는다.
- API 키·`.env`·실계정 응답을 Git에 넣지 않는다.
- HWP·VBA 보안 설정을 자동 변경하거나 우회하지 않는다.
- 외부 AI live 테스트는 사용자가 호출을 명시적으로 허용한 때만 실행한다.
- 모든 쓰기 기능은 미리보기·승인·대상 재확인·read-back을 유지한다.
- 각 Phase 종료 보고에는 변경 파일, 테스트 수, 실제 probe, 남은 제한, commit을
  기록한다.

# JARVIS PDF-2 연결·문맥·자연어 라우팅 완료 보고서

- 완료일: 2026-08-04 KST
- 작업 브랜치: `codex/pdf-capabilities`
- 범위: Python 소스, Eel API, HTML/CSS/JavaScript UI, 자동 테스트
- EXE 빌드: 수행하지 않음

## 1. 판정

PDF 기능 구현 계획의 PDF-2 범위를 소스 기준으로 완료했다.

사용자가 명시적으로 선택한 로컬 PDF 하나만 Office 편집 세션과 분리해 읽기
전용으로 연결한다. 연결 뒤에는 파일 이름, 페이지 수, 문서 유형, SHA-256 문서
fingerprint를 구조화 상태로 유지하며 실제 경로와 본문은 공개 상태에서 제외한다.

명령 파이프라인은 다음 PDF 의도를 일반 앱·AI 경로보다 먼저 결정적으로 분류한다.

- 요약, 페이지 설명, 검색, 페이지 수, 목차
- 표 추출, 보고서 작성
- 분할, 병합, 회전

페이지 수는 PDF-2에서 실제로 답한다. 본문을 사용하는 읽기 작업은 PDF-3,
파일을 만드는 변경 작업은 PDF-4가 구현되기 전까지 실행하지 않고
`missing_capability` 진단 근거와 함께 차단한다. 따라서 인식만 된 작업이 일반
AI 경로로 빠져 문서를 읽은 것처럼 답하거나, 파일 변경을 시작하는 일이 없다.

## 2. 연결 수명주기

`PdfIntakeManager`가 프로세스 안에서 PDF 연결 하나를 소유한다.

1. Windows native 선택창 또는 정확한 드롭 경로로 로컬 `.pdf`를 받는다.
2. PDF-1 판독기로 첫 페이지와 전체 파일 fingerprint, 페이지 수, 파일 크기를
   확인한다.
3. 새 `pdf-connection-<uuid>` 토큰을 만들고 기존 검색·페이지 참조를 폐기한다.
4. 읽기나 명령 실행 직전에 원본 fingerprint·페이지 수·크기를 다시 확인한다.
5. 파일이 바뀌거나 없어지면 연결을 즉시 폐기하고 재연결을 요구한다.
6. 연결 해제는 현재 connection ID가 맞을 때만 허용한다.

Office의 `FileIntakeManager`나 편집 세션에는 `.pdf`를 추가하지 않았다. PDF는
원본 변경 기능이 없는 별도 읽기 전용 경계다.

## 3. 파일 선택과 드롭

UI의 추가 메뉴에 다음 컨트롤을 추가했다.

- `PDF 연결` native 파일 선택
- PDF 파일 드롭 영역
- 연결 해제
- 채팅 상단 `PDF · 읽기 전용`, 파일 이름, 페이지 수, 문서 유형 표시

드롭은 브라우저가 실제 로컬 경로를 제공할 때 파일 이름·크기·경로를 모두
대조한다. 브라우저가 경로를 숨기면 동명 파일을 작업 폴더나 최근 폴더에서
검색하지 않는다. 사용자가 native 선택창으로 정확한 파일을 다시 고르게 한다.
이 정책 때문에 같은 이름의 PDF가 여러 개 있어도 JARVIS가 임의 파일을 고르지
않는다.

표시되는 파일 이름은 폐쇄형 schema 검증을 거친 뒤 `textContent`로만 렌더링한다.
GUI JavaScript는 직접 경로 연결 API를 사용하지 않고 선택창과 검증된 드롭 API만
사용한다.

## 4. 자연어 대상 문맥

다음 표현을 연결 PDF fingerprint와 1-base 페이지 목록으로 바꾼다.

```text
이 PDF 요약해줘            → 연결 PDF 전체
3~5페이지 설명해줘         → 3, 4, 5페이지
1, 3, 5쪽을 비교해줘       → 1, 3, 5페이지
여기 다시 설명해줘         → 직전 구조화 페이지 참조
앞 페이지 알려줘           → 직전 범위 시작 전 페이지
다음 페이지 알려줘         → 직전 범위 끝 다음 페이지
방금 찾은 부분 보여줘      → 직전 PDF 검색 결과의 근거 페이지
```

기준 페이지가 없거나 앞뒤 페이지가 문서 범위를 벗어나면 추측하지 않고 설명을
요청한다. 연결 전에는 Edge나 Acrobat에 PDF가 보인다는 이유로 파일을 선택하지
않는다. 명시된 파일 이름이 현재 연결 이름과 다르면 해당 PDF를 다시 연결하도록
안내한다.

## 5. 라우팅 경계와 기존 기능 보호

PDF 라우터는 셸 차단 뒤, native 앱·매크로·AI fallback보다 먼저 실행된다.
단, 연결된 PDF가 있다는 이유만으로 모든 `찾아줘`·`보고서 만들어줘`를 가져오지
않는다. PDF, `.pdf`, 페이지, `이거`, `여기`, 직전 검색처럼 PDF 대상을 나타내는
표현이 함께 있어야 한다.

`한글 현재 문서를 PDF로 저장해줘`, `Word를 PDF 파일로 내보내줘` 같은 Office
export 문장은 입력 PDF 명령에서 제외한다. 전체 회귀 중 이 경계의 누락으로 한글
PDF 저장 확인 테스트 1개가 처음 실패했으며, 원인을 수정하고 전용 회귀 테스트를
추가한 뒤 전체 테스트를 다시 통과시켰다.

## 6. 개인정보와 안전

- 연결 상태 공개값: connection ID, 파일 이름, fingerprint, 페이지 수, 크기,
  문서 유형, 연결 시각, 읽기 전용 표시
- persistent evidence: 파일 이름과 경로를 추가로 제외
- 검색 의도 evidence: 검색어 대신 존재 여부와 길이만 기록
- 로그: 의도 enum과 대상 페이지 수만 기록하며 경로·파일 이름·검색어를 기록하지 않음
- 마지막 검색 결과와 검색어: 프로세스 메모리에만 유지하고 연결 교체·해제 시 폐기
- 원본 PDF: PDF-2에서는 쓰기·저장·이름 변경을 수행하는 코드 경로가 없음
- 드롭: 심볼릭 링크, 이름·크기 불일치, 경로 부재를 fail-closed
- 연결 교체 경쟁: connection ID를 다시 대조해 다른 문서 결과 사용을 차단

## 7. 검증 결과

| 검사 | 결과 |
|---|---:|
| PDF-0~2 관련 표적 테스트 | 94개 통과 |
| 전체 자동 테스트 | 1,158개 통과, 조건부 3개 건너뜀 |
| Python compileall | 통과 |
| Ruff 전체 lint | 통과 |
| JavaScript `node --check` | 통과 |
| `pip check` | 통과 |
| `git diff --check` | 통과 |
| 유지보수 strict 감사 | `success=True`, 오류 0, 기존 `outputs/` 경고 1 |

PDF-1 완료 시점의 1,107개 테스트를 모두 유지하고 신규·보강 테스트 51개가
추가되었다. 표적 테스트는 계약, 페이지 선택, 검색, 연결 UI, 의도, 참조,
판독, API, 명령 라우팅, intake 수명주기를 포함한다.

Goal 자동 게이트 자체의 테스트 단계도 1,158개 통과를 확인했다. 다만 source-bound
Office·학습·워크플로 probe evidence는 PDF 변경 전 commit/tree에 묶여 있어
현재 변경 트리에서는 `probe_source_*_mismatch`로 무효다. 화면 읽기, 음성 입력,
비숙련자 관찰 역시 계속 수동 대기 상태다. 이는 PDF-2 테스트 실패가 아니라 최종
commit을 기준으로 해당 probe와 수동 수용 증거를 다시 등록해야 한다는 뜻이다.

## 9. 다음 단계와 제한

PDF-2가 완료됐다고 해서 PDF MVP 전체가 완료된 것은 아니다.

- PDF-3: 페이지 근거가 있는 요약·질문·검색 응답, 목차·표 추출,
  Word·한글·PowerPoint 산출물과 read-back 검증
- PDF-4: 분할·병합·회전의 승인, 새 출력 경로, 원자적 저장, 재열기 검증,
  중간 실패 정리
- PDF-5 선택: OCR, 암호 입력
- PDF-6 선택: Edge·Acrobat 현재 페이지와 선택 영역의 정확한 신원 연결
- PDF-7: 전체 보안·성능·실패 주입·수동 수용 검증

브라우저가 드롭 파일 경로를 숨기는 환경에서는 native 선택창을 사용해야 한다.
현재 연결은 앱 재시작 뒤 자동 복원하지 않으며, 이는 저장된 경로로 사용자 문서를
몰래 다시 읽지 않기 위한 의도된 안전 정책이다.

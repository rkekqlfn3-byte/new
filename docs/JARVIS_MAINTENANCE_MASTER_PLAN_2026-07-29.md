# JARVIS 유지보수 마스터 계획서

- 문서 버전: 1.0
- 기준일: 2026-07-29
- 적용 대상: JARVIS Prototype 1.x Python 소스 전체
- 상위 기준: `docs/JARVIS_PRODUCT_GOAL.md`, `docs/PRODUCT_GOAL_ACCEPTANCE.md`
- 운영 원칙: 개발 단계에서는 Python 소스만 실행·검증하며, EXE는 사용자가 별도로 지시할 때만 생성한다.

---

## 1. 목적

이 문서는 JARVIS를 기능이 늘어나도 고치기 쉽고, 잘못된 수정이 기존 기능을 깨뜨리지 않으며, 문제가 발생했을 때 원인과 책임 영역을 빠르게 찾을 수 있는 구조로 유지하기 위한 단일 기준서다.

유지보수의 최종 목표는 다음 네 가지다.

1. 사용자의 자연어, 현재 문맥, 실제 앱 조작이라는 제품 목표를 훼손하지 않는다.
2. 한 모듈의 변경이 다른 영역으로 예측 불가능하게 전파되지 않게 한다.
3. 안전·확인·검증·복구 규칙은 기능 개발보다 우선한다.
4. 모든 변경은 재현 가능한 테스트와 기록을 남긴다.

---

## 2. 절대 원칙

### 2.1 제품 원칙

- 사용자는 명령어 문법을 외우지 않고 평소 말로 요청한다.
- JARVIS는 활성 앱, 문서, 선택 영역, 직전 행동을 근거로 대상을 판단한다.
- 실제 앱 조작은 좌표 클릭보다 COM, 공식 API, UI Automation의 구조적 대상을 우선한다.
- 변경 작업은 대상 확인, 필요 시 승인, 실행, 결과 재조회, 검증 순서로 처리한다.
- 실패는 기능 미구현, 코드 결함, 사용자 설명 부족, 권한·환경 문제, 취향 차이로 구분한다.
- 학습은 검증된 성공과 반복된 사용자 교정에 근거하며, 한 번의 표현을 성급하게 일반화하지 않는다.

### 2.2 개발 원칙

- `engine/parser.py`는 파사드이자 조립 지점이다. 세부 파싱과 실행 로직을 다시 넣지 않는다.
- 자식 객체 생성자에 `CommandParser` 전체나 상위 매니저의 `self` 전체를 전달하지 않는다.
- 자식 객체가 `parser`, `_parser`, `owner` 같은 영구 역참조를 보관하지 않는다.
- 의존성은 필요한 함수, 저장소, 정책 객체, 서비스 묶음만 명시적으로 주입한다.
- 실행 중에만 필요한 문맥은 메서드 인자나 짧은 수명의 runtime context로 전달한다.
- 공개 파사드의 단순 위임 메서드는 호환성 근거가 없으면 만들지 않는다.
- 동적 Python, 셸, 레지스트리, 파일 삭제·덮어쓰기 등 위험 작업은 fail-closed가 기본이다.
- API 키, 토큰, 개인 문서 내용, 사용자 경로가 저장소나 일반 로그에 들어가면 안 된다.
- 사용자 파일과 사용자 데이터는 테스트 자산으로 직접 사용하지 않는다.

## 3. 현재 기준선

이 계획서 작성 시점의 정상 기준은 다음과 같다.

- `CommandParser`의 native static alias와 단순 위임 메서드가 제거되어 있다.
- 확인 흐름은 `ConfirmationRegistry` 아래에서 상태, 생성, 응답, 디스패치를 관리한다.
- 파서와 주요 하위 서비스의 양방향 영구 참조가 제거되어 있다.
- `SkillExecutionServices`가 스킬 실행 의존성을 명시적으로 묶는다.
- 파서 구성 계약을 `tests/unit/test_parser_composition.py`가 검사한다.
- 전체 자동 테스트 1,043개 통과, 3개 환경 조건부 건너뜀 상태가 2026-07-29
  감사 수정 후 검증 기준이다.
- 1,000문장 수용성 배터리와 Stage 12 진단 코퍼스가 통과 상태다.

이 숫자는 영구 목표치가 아니라 기준선이다. 테스트가 추가되면 총 개수는 증가할 수 있지만, 기존 테스트 삭제나 완화는 사유와 대체 검증 없이 허용하지 않는다.

## 4. 모듈 책임 지도

| 영역 | 주 책임 | 허용되는 의존성 | 두지 말아야 할 책임 |
|---|---|---|---|
| `engine/parser.py` | 구성, 공개 진입점, 결과 조합 | 하위 서비스의 명시적 인터페이스 | 세부 문장 규칙, OS 직접 조작, 확인 상태 구현 |
| `engine/parsing/` | 순수 자연어 해석, native 명령 구조화 | 정규화 유틸, 불변 데이터 | 앱 실행, UI 상태 변경, 저장소 쓰기 |
| `engine/pipeline/` | 명령 처리 순서와 라우팅 | parser 서비스 인터페이스 | 장기 상태 소유, 앱별 세부 COM 코드 |
| `engine/confirmation/` | 승인 대기, 승인 문구, 응답, 재개 | 정책, pending 저장소, 실행 콜백 | 자연어 전체 파싱, 앱 자동화 구현 |
| `engine/app_actions/` | Excel·Word·PowerPoint·한글 등 네이티브 작업 | 앱 어댑터, 실행 결과 계약 | 대화 기록, 사용자 학습 정책 |
| `engine/edit_mode/` | 문서 연결, 선택·포커스 문맥, 연속 편집 | 앱 어댑터, 문맥 저장소 | 일반 질문 라우팅, 동적 코드 생성 |
| `engine/skills/` | 검증된 작업 재사용, 실행 정책, 사후조건 | 제한된 실행 서비스, 스킬 저장소 | 무승인 권한 확대, 임의 전역 상태 접근 |
| `engine/security/` | 위험도, 허용 목록, 비밀정보 보호 | 명령·실행 메타데이터 | 편의상 정책 우회 |
| `engine/diagnostics/` | 실패 분류, 재현 정보, 복구 안내 | 구조화된 실행 결과 | 민감 원문 무제한 기록 |
| `verification/` | 제품·Windows·성능·릴리스 검증 | 공개 진입점과 테스트 더블 | 운영 코드의 비공개 내부 상태 의존 |
| `tests/` | 회귀 방지와 계약 검증 | 공개 계약, 필요한 최소 내부 계약 | 실제 사용자 파일 변경, 외부 서비스 기본 호출 |

새 코드를 넣을 위치가 애매하면 다음 순서로 판단한다.

1. 입력을 해석만 하는가? `parsing`.
2. 순서와 분기를 결정하는가? `pipeline`.
3. 승인을 보관·재개하는가? `confirmation`.
4. 실제 앱을 조작하는가? `app_actions` 또는 앱별 adapter.
5. 반복 작업을 저장·재생하는가? `skills`.
6. 여러 영역을 조립만 하는가? `parser`.

## 5. 아키텍처 보호 규칙

### 5.1 파서 파사드 예산

- `engine/parser.py`는 원칙적으로 1,000줄 이하를 유지한다.
- 1,000줄을 넘기면 새 기능 추가 전에 분리 검토를 수행한다.
- 파서에 `_parse_native_*` alias를 다시 만들지 않는다.
- 하위 모듈이 파서 내부 필드를 직접 읽는 방식으로 기능을 추가하지 않는다.
- 호환성용 위임 메서드가 꼭 필요하면 제거 예정일, 호출자, 테스트를 함께 기록한다.

### 5.2 의존성 방향

허용 방향은 대체로 다음과 같다.

```text
UI/API -> CommandParser facade -> pipeline/manager -> domain service -> adapter
                                                        |
                                                        -> structured result
```

금지 패턴은 다음과 같다.

```text
child -> parser 전체 참조
adapter -> UI 직접 갱신
parser -> 앱별 COM 세부 구현
domain service -> 전역 singleton에서 임의 상태 조회
```

### 5.3 상태 소유권

- 승인 대기 상태는 `ConfirmationRegistry`가 소유한다.
- 편집 대상과 선택 문맥은 edit session/context 계층이 소유한다.
- 학습 후보와 활성 스킬은 각각 지정된 저장소가 소유한다.
- 동일 상태를 두 객체가 복제해 보관하지 않는다.
- 캐시는 원본이 아니며, 언제든 원본에서 재생성 가능해야 한다.

### 5.4 결과 계약

모든 실행 경로는 가능한 한 구조화된 결과를 반환한다.

- 성공 여부
- 수행한 행동
- 실제 대상
- 변경 전후 또는 검증 근거
- 실패 분류
- 사용자에게 보여줄 안전한 메시지
- 재시도 가능 여부

문자열 메시지만 반환해 성공을 추정하는 새 경로는 만들지 않는다.

## 6. 변경 등급과 필수 검증

| 등급 | 예시 | 최소 검증 |
|---|---|---|
| A: 문서·문구 | 설명, 오탈자, 비동작 UI 문구 | diff 확인, 관련 렌더·문자열 테스트 |
| B: 순수 로직 | 파싱, 정규화, 포맷팅 | 관련 unit + integration + 1,000문장 배터리 |
| C: 상태·정책 | 확인, 학습, 보안, 세션 | unit + integration + 전체 테스트 + 실패 주입 |
| D: 네이티브 앱 | Excel/Word/PPT/한글, 포커스·선택 | 전체 테스트 + Windows 테스트 + 앱별 probe + 수동 확인 |
| E: 저장·배포 | 마이그레이션, 백업, 릴리스 | 전체 게이트 + 복구 실험 + 보안 감사 + clean archive |

등급은 변경 파일 수가 아니라 실패 시 영향으로 정한다. 여러 등급에 걸치면 가장 높은 등급을 적용한다.

## 7. 표준 개발 절차

### 7.1 작업 시작 전

1. `git status --short`로 사용자 변경과 기존 미추적 파일을 확인한다.
2. 관련 문서, 코드, 테스트를 읽고 현재 계약을 적는다.
3. 버그는 수정 전에 재현 테스트를 만든다.
4. 기능은 정상 경로, 애매한 표현, 거부·실패 경로를 함께 설계한다.
5. 큰 변경은 파싱, 정책, 실행, UI를 한 번에 섞지 않고 작은 단위로 나눈다.

### 7.2 구현 중

- 기존 사용자 변경을 덮어쓰지 않는다.
- 새 의존성은 생성자 또는 명명된 service bundle에 추가한다.
- 테스트 때문에 운영 코드에 우회 플래그를 넣지 않는다.
- 실제 앱이 없는 테스트는 test double을 사용하되, Windows probe로 계약 차이를 보완한다.
- 로그에는 대상 타입과 식별 가능한 안전한 메타데이터만 남기고 문서 본문은 기본적으로 남기지 않는다.
- 실패를 `except Exception: pass`로 숨기지 않는다.

### 7.3 완료 전

1. 변경 파일의 문법과 import를 검사한다.
2. 관련 집중 테스트를 통과시킨다.
3. 전체 자동 테스트를 통과시킨다.
4. 제품 수용성 배터리와 해당 probe를 통과시킨다.
5. `git diff --check`로 공백·CRLF 문제를 확인한다.
6. diff에 비밀정보, 생성물, 사용자 파일이 없는지 확인한다.
7. 변경 이유, 검증 결과, 남은 위험을 보고한다.

## 8. 테스트 피라미드와 실행 게이트

프로젝트 가상환경이 있으면 아래 명령의 `python`을 `.venv\Scripts\python.exe`로 바꿔 실행한다.

### 8.1 빠른 게이트

작은 수정마다 실행한다.

```powershell
python -m compileall -q engine verification tests
python -m unittest -q tests.unit.test_parser_composition
python -m unittest -q <변경 영역의 테스트 모듈>
git diff --check
```

### 8.2 전체 자동 게이트

병합·체크포인트 전 반드시 실행한다.

```powershell
python -m unittest -q
python -m engine.startup_check
python -m verification.utterance_acceptance_battery
python -m verification.prototype11_stage12_probe
python -m verification.product_goal_acceptance --automated-only
```

### 8.3 영역별 추가 게이트

- 자연어·라우팅: `verification.utterance_acceptance_battery`
- 자기 진단: `verification.prototype11_stage12_probe`, 실패 주입 도구
- Excel: Excel unit/integration/windows 테스트와 관련 COM probe
- Word/PPT/한글: 해당 Windows 테스트와 실제 앱 수동 probe
- 보안·동적 실행: run policy, dynamic preflight, release security audit
- 저장소·학습: atomic storage, persistence, dictionary locking, learning loop
- 성능: `verification.maintenance_performance`, `verification.stage12_performance`
- 릴리스: `verification.release_security_audit`, 소스 archive 검증

### 8.4 수동 테스트가 필요한 조건

다음은 자동 테스트만으로 완료 처리하지 않는다.

- 실제 Office 앱의 포커스와 맨 앞으로 가져오기
- 선택 영역 표시와 편집 중 선택 유지
- 저장하지 않은 새 문서 연결·편집
- COM 인스턴스가 여러 개일 때 현재 문서 선택
- Windows 음량 상대 조절과 장치 차이
- 한글 UI Automation과 보안 모듈 상호작용
- 화면 배율, 다중 모니터, 접근성 설정에 따른 오버레이

수동 테스트는 문장, 사전 조건, 실제 결과, 기대 결과, 스크린샷, 로그 ID를 기록한다.

### 8.5 자동 유지보수 도구

현재 변경된 파일을 기준으로 필요한 검증 명령과 수동 확인 항목을 조회한다.

```powershell
python -m verification.test_gate_selector
```

특정 파일의 변경 영향을 미리 확인할 수도 있다.

```powershell
python -m verification.test_gate_selector engine/parser.py engine/confirmation/confirmation_registry.py
```

구조, 비밀정보, 추적 금지 산출물, 대용량 파일을 읽기 전용으로 감사한다.

```powershell
python -m verification.maintenance_audit
```

기본 모드는 오류만 실패로 처리하고 생성 디렉터리·대용량 파일은 경고한다. 정리 상태까지 통과 조건으로 삼을 때만 `--strict`를 사용한다.

```powershell
python -m verification.maintenance_audit --strict
```

두 도구 모두 자동 보고서 연동을 위한 `--json` 출력을 지원한다. 감사 결과에는 발견된 비밀값 자체를 출력하지 않는다.

확인 만료, 승인 거부, 반복 대상 변경, 원자 저장 실패, 백업 복구 잠금, COM busy, 검증·롤백 실패는 실제 사용자 문서나 앱을 열지 않는 격리된 실패 주입으로 확인한다.

```powershell
python -m verification.maintenance_failure_injection
```

Python 소스만으로 시작 사전 점검, 파서 생성, 로컬 해석·명령, 결과 정규화,
원자적 JSON 저장의 p95와 소스 크기를 기준선과 비교한다. 이 검증은 EXE를
실행하거나 생성하지 않고, 격리된 임시 데이터만 사용하며 외부 AI를 호출하지 않는다.

```powershell
python -m verification.maintenance_performance
```

기준값은 `verification/maintenance_performance_baseline.json`에 보관한다. 새 기준선은
동일한 컴퓨터에서 전체 회귀가 통과한 뒤 의도적인 구조·성능 변화가 확인된 경우에만
갱신한다. 단순히 게이트를 통과시키기 위해 기준값이나 허용 한도를 올리지 않는다.

## 9. 회귀 방지 계약

다음 항목은 변경 때마다 특별히 보호한다.

### 9.1 자연어

- 절대값과 상대값을 구분한다. 예: “소리 10으로”와 “소리 10 내려”.
- “조금”, “약간”, “더”, “덜” 같은 상대 표현은 기본 증감 규칙을 갖는다.
- 날짜, 시간, 날씨, 일반 질문을 동적 코드로 보내지 않는다.
- 위험한 명령을 무해한 실행 파일명이나 `echo`로 오인해 통과시키지 않는다.
- 애매한 대상은 추측 실행보다 짧은 재질문을 우선한다.

### 9.2 문서 문맥

- 문맥 표시에는 기본적으로 앱, 문서, 시트·슬라이드·섹션, 범위 주소만 사용한다.
- 셀 값이나 선택 내용은 사용자가 요청하지 않으면 문맥 라벨에 노출하지 않는다.
- 새로 열린 다른 Office 문서도 다시 탐색해 연결할 수 있어야 한다.
- 저장하지 않은 문서도 안정적인 runtime identity로 편집 가능해야 한다.
- 연결 버튼은 해당 문서를 맨 앞으로 가져와야 한다.

### 9.3 확인과 보안

- 외부 상태를 바꾸지 않는 날짜·시간·날씨 응답은 불필요한 실행 확인을 요구하지 않는다.
- 외부 상태 변경, 파일 쓰기, 동적 코드, 셸, 민감 설정은 정책에 따라 확인한다.
- 확인 대기 중 대상이 바뀌면 원래 대상과 현재 대상을 재검증한다.
- 거부, 만료, 재시작 후 복원 각각을 테스트한다.

### 9.4 학습과 재사용

- 실패한 행동을 활성 스킬로 승격하지 않는다.
- 성공 결과를 사후조건으로 확인한 뒤 재사용한다.
- 위험도가 높아지면 기존 학습보다 현재 보안 정책이 우선한다.
- 사용자 교정은 원문 전체보다 구조화된 선호와 근거 횟수를 저장한다.

## 10. 성능 유지 기준

성능은 절대 수치와 회귀율을 함께 본다.

- 로컬 명령의 UI 응답 목표는 1초 이내다.
- 파싱·라우팅 벤치마크의 중앙값 또는 p95가 기존 기준보다 20% 이상 악화되면 원인을 분석한다.
- 외부 AI 호출은 로컬 규칙, 활성 스킬, 캐시로 해결할 수 없을 때만 사용한다.
- Office 연결 탐색은 무제한 polling하지 않고 제한 시간과 취소 경로를 둔다.
- 시작 시간, 메모리, 저장소 크기는 월 1회 기록해 추세를 본다.
- 성능 개선 때문에 안전 검증이나 결과 재조회를 생략하지 않는다.

성능 기준을 바꿀 때는 실제 사용자 체감 측정과 `verification.stage12_performance` 결과를 함께 남긴다.

## 11. 보안·개인정보·비밀정보

### 11.1 저장소 반입 금지

- API 키, access token, refresh token, 비밀번호
- `.env` 실값, 인증 캐시, 브라우저 프로필
- 실제 사용자의 문서, 대화 원문, 개인 식별 정보
- 로컬 절대 경로가 포함된 개인 설정 백업
- 빌드 산출물, 대용량 임시 파일, 테스트 중 생성된 Office 파일

저장소가 비공개여도 위 항목은 커밋하지 않는다. 비공개 저장소는 비밀 저장소가 아니다.

### 11.2 실행 안전

- 동적 작업은 실행 전에 정적 검사와 runtime 제한을 모두 적용한다.
- 허용 목록은 실행 파일 이름만 보지 말고 인자와 최종 행동을 평가한다.
- 파일 쓰기는 대상 경로, 덮어쓰기, 확장자, 현재 문서 identity를 확인한다.
- 복구 불가능한 변경은 사전 승인과 가능한 백업을 요구한다.
- 로그와 보고서에는 문서 내용 대신 해시, 타입, 길이, 익명 ID를 사용한다.

### 11.3 정기 보안 감사

- 매 릴리스: 비밀정보 검색, 위험 API 사용 검색, dependency 변경 검토
- 매월: 허용 목록과 확인 예외 검토
- 분기별: 위협 모델과 복구 절차 재검증

## 12. 데이터와 마이그레이션

- 모든 영구 쓰기는 atomic write 또는 동등한 안전성을 보장한다.
- 스키마에는 명시적 버전을 둔다.
- 마이그레이션은 여러 번 실행해도 결과가 같아야 한다.
- 마이그레이션 전 백업, 완료 후 검증, 실패 시 이전 버전 복구 경로를 제공한다.
- 잘못되거나 부분 저장된 항목 하나 때문에 전체 저장소를 읽지 못하게 해서는 안 된다.
- 테스트는 빈 저장소, 구버전, 손상 일부, 동시 접근, 디스크 쓰기 실패를 포함한다.
- 사용자 학습 데이터와 애플리케이션 기본 데이터는 분리한다.

## 13. 의존성 관리

- 새 라이브러리는 표준 라이브러리나 기존 의존성으로 해결할 수 없는지 먼저 확인한다.

- 제거 가능한 의존성은 분기별로 검토한다.
- Office 자동화 라이브러리 업데이트는 설치된 실제 Office 버전과 함께 검증한다.

## 14. 장애 대응과 실패 책임 분류

### 14.1 심각도

| 등급 | 기준 | 대응 |
|---|---|---|
| S0 | 데이터 손실, 무승인 위험 실행, 비밀정보 노출 | 즉시 기능 중지, 영향 차단, 복구·감사 우선 |
| S1 | 잘못된 문서 수정, 확인 우회, 반복 충돌 | 해당 경로 비활성화 또는 롤백 후 당일 분석 |
| S2 | 주요 명령 실패, 앱 연결·포커스·선택 회귀 | 재현 자료 확보 후 다음 수정 우선순위 |
| S3 | 문구, 레이아웃, 드문 표현 인식 문제 | 일반 유지보수 목록에서 처리 |

### 14.2 책임 분류

실패 보고에는 반드시 다음 중 하나를 기록한다.

- `JARVIS_RETRYABLE`: 다른 탐색이나 재시도로 자체 해결 가능
- `USER_INPUT_REQUIRED`: 대상이나 의도가 부족해 사용자 설명 필요
- `NOT_IMPLEMENTED`: 기능 계약 자체가 없음
- `PRODUCT_BUG`: 기존 계약과 다른 동작
- `ENVIRONMENT_BLOCKED`: 권한, 앱 설치, 보안 정책, COM 상태 문제
- `PREFERENCE_MISMATCH`: 결과는 유효하지만 사용자 선호와 다름

### 14.3 장애 처리 순서

1. 위험한 실행을 중단하고 사용자 파일을 보호한다.
2. 명령, 앱 상태, 대상 identity, 실행 단계, 구조화된 결과를 확보한다.
3. 최소 재현 테스트를 만든다.
4. 책임 영역과 심각도를 분류한다.
5. 수정 또는 안전한 우회책을 적용한다.
6. 집중·전체·제품 수용성 테스트를 다시 실행한다.
7. 재발 방지 계약과 문서를 갱신한다.

## 15. Git과 변경 기록

- 작업 전후 `git status --short`를 확인한다.
- Codex가 새 작업 브랜치를 만들 때 기본 이름은 `codex/<작업명>`을 사용한다.
- 커밋은 한 가지 의도만 담고, 리팩터링과 동작 변경을 가능하면 분리한다.
- 커밋 메시지는 결과보다 변경 이유와 보호한 계약을 드러낸다.
- 테스트 실패 상태, API 키, 사용자 데이터, 임시 보고서는 커밋하지 않는다.
- 생성 보고서 중 재현에 필요한 요약만 저장하고 민감하거나 기계별인 원본은 제외한다.
- 기존 사용자의 변경을 자동으로 stage하거나 되돌리지 않는다.
- 태그와 원격 push는 사용자의 요청 또는 승인 후 수행한다.

권장 커밋 구조 예시는 다음과 같다.

```text
refactor(parser): inject explicit dependencies into child services
fix(confirmation): revalidate target before confirmed execution
test(excel): cover unsaved workbook reconnect behavior
docs(maintenance): define release and incident gates
```

## 16. 릴리스와 백업 절차

개발 체크포인트 또는 Prototype 태그를 만들 때 다음 순서를 따른다.

1. CRLF와 공백 오류를 정리하고 `git diff --check`를 통과한다.
2. 전체 자동 테스트와 제품 수용성 검증을 통과한다.
3. 관련 실제 Windows·Office probe를 실행한다.
4. 비밀정보·사용자 데이터·불필요한 생성물 반입 여부를 감사한다.
5. 변경 범위별 clean commit을 만든다.
6. commit identity가 포함된 Windows probe를 다시 실행한다.
7. 릴리스 노트와 알려진 제한을 작성한다.
8. 사용자가 요청한 경우에만 Prototype 태그를 생성한다.
9. `git archive` 기반으로 추적된 최종 소스만 백업한다.
10. archive를 새 임시 디렉터리에 풀어 시작 검사와 핵심 테스트를 재실행한다.

EXE 생성은 이 절차에 자동 포함되지 않는다. 사용자가 명시적으로 요청한 별도 작업으로만 수행한다.

```text
재현 횟수:
위험하거나 잘못 변경된 내용:
스크린샷/로그 ID:
```

개발 결과 보고는 다음 형식을 사용한다.

```text
변경 요약:
원인:
수정한 계약:
추가·수정한 테스트:
실행한 전체 검증:
남은 제한:
사용자가 직접 확인할 항목:
```

## 21. Definition of Done

다음 조건을 모두 만족해야 “수정 완료”라고 보고한다.

- 요청한 동작이 실제 코드에 구현되었다.
- 재현 테스트가 수정 전 실패하고 수정 후 통과하거나, 동등한 회귀 테스트가 추가되었다.
- 관련 unit, integration, 전체 자동 테스트가 통과했다.
- 변경 등급에 맞는 제품·Windows·수동 검증이 완료되었다.
- 위험 작업의 확인, 대상 재검증, 실패 복구가 유지된다.
- 민감정보와 사용자 파일이 변경 목록에 없다.
- 문서, UI 설명, 테스트 문장이 새 동작과 일치한다.
- 성능과 시작 동작에 허용 불가능한 회귀가 없다.
- 남은 제한을 숨기지 않고 사용자에게 명시했다.
- EXE, commit, tag, push 등 별도 권한이 필요한 작업을 임의로 수행하지 않았다.

## 22. 이 문서의 관리

- 아키텍처 책임, 테스트 명령, 보안 정책, 릴리스 절차가 바뀌면 같은 변경에서 이 문서도 갱신한다.
- 실제 코드와 충돌하면 코드를 무조건 정답으로 보지 말고 제품 Goal과 수용성 계약을 기준으로 둘 중 무엇을 수정할지 판단한다.
- 변경 이력은 Git으로 관리하며 문서 본문에는 최신 유효 기준만 유지한다.
- 최소 분기 1회 전체 내용을 검토한다.

이 계획서의 핵심 판단 기준은 하나다.

> 기능을 더 추가하는 것이 JARVIS를 발전시키는 일이 아니라, 사용자의 말과 문맥을 안전하고 검증 가능하게 실제 행동으로 바꾸는 능력을 오래 유지하는 것이 발전이다.

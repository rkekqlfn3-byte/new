# Prototype 1.1 9단계 Excel VBA 편집

## 목표와 현재 상태

Excel 매크로 사용 통합문서의 VBA 프로젝트를 구조화된 읽기·분석·수정·실행
경계에 연결했다. 현재 소스 구현, 실패 복원, 보안 차단 진단과 자동 회귀를
완료했고, 이 PC의 소유 `.xlsm`에서 실제 VBA 읽기·분석·백업·수정·복원·실행과
셀 후조건까지 통과했다. 따라서 9단계는 **코드·안전 경계와 실 VBA 검증 완료**로
판정한다.

`vba_trust_status`는 Excel을 실행하거나 레지스트리를 수정하지 않고 관련 설정을
읽기만 한다. 실제 COM 접근이 거부되면 `VbaTrustAccessBlocked`가
`blocked_reason=vba_trust_access`, `retryable=false`, `state_changed=false`와
함께 필요한 사용자 조치를 명시한다. 일반 COM 오류를 신뢰 설정 오류로 오인하지
않으며 API 응답에도 실패 단계와 진단 문맥을 보존한다.

## 지원 범위

- `.xlsm`, `.xlsb`의 VBA 프로젝트 포함 여부 감지
- 모듈과 `Sub`·`Function`·Property 프로시저 목록
- 단일 모듈 코드 읽기
- 반복문·Range·Worksheet·저장 동작 설명
- 오류 은폐, 활성 선택 의존, Shell·파일·네트워크·레지스트리 위험 분석
- 변경 전후 unified diff 미리보기
- 표준 모듈 원본 `.bas` 백업 후 승인 기반 코드 교체
- 적용 결과 digest 재검증과 실패 시 원문 자동 복원
- 직전 JARVIS VBA 코드 수정의 구조화된 원문 복원
- 인수가 없는 `Public Sub`의 별도 승인 실행

다음 요청을 제한된 로컬 규칙으로 해석한다.

```text
“VBA 모듈 목록 보여줘.”
“Module1 코드 보여줘.”
“이 매크로가 무슨 일을 해?”
“마지막 행을 잘못 찾는데 고쳐줘.”
“선택한 범위만 처리하도록 바꿔.”
“실행 전에 원본 시트를 백업하도록 해.”
“Module1의 ExportReport 매크로 실행해줘.”
```

임의 코드를 자유 생성하지 않는다. 일반 교체는 변경 전·후 코드 조각을 각각
따옴표로 지정해야 하며 정확히 한 곳이 일치할 때만 수정안을 만든다.

## 위험 정책

| 작업 | 정책 |
|---|---|
| 프로젝트·모듈·코드 읽기와 정적 설명 | 자동 허용 |
| VBA 코드 수정 | diff 미리보기와 승인 필수 |
| 매크로 실행 | 코드 수정과 분리된 별도 승인 필수 |
| Shell·파일 삭제·네트워크·레지스트리 포함 | 강한 경고와 두 번째 승인 필수 |

코드는 읽기·분석 단계에서 데이터로만 취급한다. 보안 센터 설정, 매크로 보안
수준, 레지스트리는 JARVIS가 변경하지 않는다. 실행 대상은 현재 연결된 정확한
통합문서의 표준 모듈에 있는 인수 없는 `Public Sub` 하나로 제한한다.

## 백업과 복원

코드를 수정할 때 다음 순서를 고정한다.

```text
승인 직전 문서·모듈 digest 재확인
→ %LOCALAPPDATA%\Jarvis\data\vba_backups 아래에 원본 .bas Export
→ 백업 파일 존재·크기 확인
→ 모듈 코드 교체
→ 변경 후 digest 재읽기
→ 실패하면 메모리의 원문 코드로 즉시 복원
```

백업 생성이 실패하면 모듈을 건드리지 않는다. 승인 대기 중 사용자가 코드를
바꾸면 백업·적용 모두 수행하지 않고 새 미리보기를 요구한다. 성공한 수정은
`방금 거 취소해`로 현재 코드가 직전 수정 결과와 같을 때만 원문 복원할 수 있다.

## 안전 한도

- 한 모듈 최대 50,000자
- 한 프로젝트 최대 100개 모듈
- 코드 수정은 표준 모듈만 지원
- 잠긴 VBA 프로젝트, 읽기 전용 통합문서 수정, `.xlsx/.xls`는 차단
- 여러 모듈·프로시저가 후보면 이름을 지정하기 전까지 차단
- Private Sub, Function, 인수 있는 Sub는 실행하지 않음
- 매크로 실행은 동기 COM 호출이므로 장시간 실행되는 매크로의 강제 중단은
  아직 지원하지 않음
- `Application.Run()`의 COM 오류 없는 반환은 프로시저 호출 완료만 검증한다.
  셀·파일 등 업무 결과는 별도 후조건이 없으면 검증 완료로 표시하지 않는다.

## 자동 검증

```powershell
python -m tests.test_runner all -q
```

2026-07-17 독립 감사 후속 보완까지 포함한 전체 자동 회귀 632개 중 629개가
통과했고, 외부 AI 실계정 테스트 3개는 skip됐으며 실패는 0개다. 새 테스트는
다음을 확인한다.

- 자연어 요청의 VBA 허용 작업 변환
- 프로시저 목록과 실행 가능 여부 판정
- 위험 기능 정적 탐지
- `.xlsm/.xlsb`, VBA 없음, 잠금, 읽기 전용 차단
- 원본 백업 후 수정·digest 검증·실패 복원·직전 수정 취소
- 승인 뒤 코드 변경 시 실행 차단
- 안전 매크로 1회 승인과 위험 매크로 2회 승인
- 미리보기나 첫 승인 단계에서 매크로가 실행되지 않음
- 신뢰 설정 상태 조회가 Excel이나 레지스트리를 변경하지 않음
- 신뢰 차단과 일반 VBA 오류를 구분하고 API까지 진단 문맥을 전달함
- 코드 쓰기와 복원이 모두 실패해도 외부 `.bas` 백업을 보존함

## 실제 Excel 검증

```powershell
python -m verification.prototype11_stage9_probe
```

검증 도구는 실행 중인 사용자 Excel이 있으면 시작하지 않으며, 별도 Excel
프로세스와 JARVIS 소유 임시 `.xlsm`만 사용한다. 2026-07-17 최종 실행에서는
프로젝트·모듈·프로시저 탐색, 코드 읽기·설명, 위험 기능 분석, 외부 `.bas` 백업,
수정·검증·원문 복원, 별도 매크로 실행과 A1의 실제 업무 결과를 모두 통과했다.
`Application.Run()` 반환 자체는 호출 경계로만 표시되고, A1 확인은 프로브의
별도 후조건으로 판정됐다. 보안 설정과 사용자 문서는 변경하지 않았다.

이 Office 빌드에서는 VBProject 접근 뒤 `Quit()`만으로 소유 Excel 프로세스가
종료되지 않아, 검증 시작 전 존재하지 않았고 검증 중 생성된 PID만 추적해 정리하는
폴백을 사용했다. 기존 사용자 Excel이 있으면 프로브 자체를 건너뛴다.

## 1. 작업 목적 (원안 유지)

새 업무 기능 추가가 아니라, 이번 달 안에 다음 상태를 완성한다.

> 사용자의 명령을 이해하고, 정보가 부족하면 되물어보고, 실행 과정을
> 자연어로 설명하고, 결과를 검증하며, 잘못된 작업은 되돌릴 수 있는 상태.

이후 기능 개발 중심 단계를 종료하고 실제 사용자 표현·예외 검증 테스트로
전환한다.

## 2. 핵심 범위 (원안 유지)

1. 터미널·실행 과정의 자연어화
2. 애매하거나 정보가 부족한 명령의 되물어보기
3. 실행 완료 후 되돌리기 UI 연결

기반 정리: 실행 이벤트 정규화, 성공·실패·검증 표현 통일, 개발 로그와
사용자 설명 분리, Excel 완료 기준 확정, 기능 동결·테스트 전환 기준 확정.

## 3. 최우선 원칙 (원안 유지 + 1항 보강)

- **3.1 기존 구조 재사용** — 원안의 재사용 목록은 실측으로 확인됐다.
  보강: *이벤트도 재사용 대상이다.* `execution_controller.event(...)`
  (parser·pipeline·skill_executor에서 이미 사용 중),
  `normalize_execution_result`, 확인 카드 payload, `undo_available`,
  read-back 검증 결과가 이미 구조화되어 있으므로 **새 계층은 이것들을
  받아 정규화·표현하는 소비자**로만 만든다.
- **3.2 원본 로그 비삭제** — 유지.
- **3.3 로그 한 줄마다 API 호출 금지** — 유지. 기본 설명은 구조화
  이벤트 + 로컬 템플릿. API는 미분류 예외·복잡한 모호성 선택지 생성에만
  보조 사용하고, API 장애 시에도 기본 설명이 동작해야 한다.

## 4. 목표 사용자 경험 (원안 유지)

원안 4.1~4.5의 다섯 시나리오(정상 실행, 애매한 명령, 정보 부족, 실패,
되돌리기)를 수용 기준으로 삼는다. 단 4.3의 추천 흐름은 8.4의 개정 정의
(추천값 채운 미리보기)를 따른다.

## 5. 구조 변경안 (개정)

```text
사용자 명령
→ 의도 분석 (기존: 로컬 사전·학습 → 편집 intent 분석기 → AI 최후순)
→ 필수 정보·모호성 검사
    ├─ 충분: 미리보기 준비 (기존 승인 계약 그대로)
    └─ 부족: clarification_required (기존 확인 카드 재사용)
→ [기존] execution_controller.event / 실행 결과 / 검증 결과 발생
→ [신규] user_feedback 정규화: 기존 이벤트·결과 → 표준 이벤트 모델
→ [신규] 로컬 템플릿 렌더링 → 사용자용 진행·완료·실패 문장
→ [기존] read-back 검증, undo 기록
→ [신규] 되돌리기 버튼 노출 (undo_available=True일 때만)
→ 원본 로그는 기존 _log_to_terminal 경로로 상세 영역에 계속 저장
```

핵심: **발생(기존) / 정규화·표현(신규)**의 단방향 계층. 실행 코드에는
이벤트 발생 지점을 추가할 수는 있어도, 병렬 이벤트 체계를 만들지 않는다.

## 6. 작업 1: 실행 이벤트 정규화 (개정)

### 6.1 이벤트 모델 (원안 유지)

원안의 필드 구조를 그대로 쓴다: `event_type`, `stage`, `app`, `action`,
`target{sheet,range}`, `details{}`, `success`, `verified`,
`undo_available`, `technical_message`. 이벤트 종류 15종(원안 6.2)도 유지.

### 6.2 신규 모듈 (역할 재정의)

```text
engine/user_feedback/
    __init__.py
    event_models.py      # 이벤트 필드·정규화 규칙
    event_adapter.py     # [개정] 기존 발생원 → 표준 이벤트 변환
    natural_language_renderer.py
    templates.py
```

`event_dispatcher.py`(발생·배포)를 `event_adapter.py`(수집·변환)로
바꾼다. 변환 대상 발생원:

| 기존 발생원 | 매핑 이벤트 |
|---|---|
| `execute_command_result` 진입 | `request_received` |
| 로컬 분석·편집 intent 확정 | `intent_resolved` |
| `confirmation_required`/`clarification_required` 반환 | `clarification_required` |
| 미리보기 생성 | `action_preparing` |
| 승인 후 실행 시작 | `action_started` |
| `normalize_execution_result` 성공 | `action_completed` |
| read-back 검증 결과 (`verified`) | `verification_passed/failed` |
| 실패 결과 (`error_type` 포함) | `action_failed` |
| `undo_last_edit` 흐름 | `rollback_started/completed/failed` |
| 사용자 취소 | `action_cancelled` |

### 6.3 UI 전달 (원안 유지)

`_log_to_terminal()`은 그대로 두고 `_send_user_event(event)`
(`eel.receive_user_event`)를 별도로 추가한다. 두 채널을 섞지 않는다.

### 6.4 이벤트 개인정보 경계 (신설)

- 화면 표시용 이벤트에는 시트명·범위 주소·행 수 같은 **구조 정보만**
  담는다. 셀 값·문서 본문은 기존 미리보기 경로가 이미 담당하므로
  이벤트에 중복 저장하지 않는다.
- **파일로 영구 저장되는 이벤트 로그**는 기존 진단 원칙을 따른다:
  문서 내용·전체 경로·사용자 원문 저장 금지, 해시·불리언·횟수·구조
  정보만 저장.
- `technical_message`는 화면 기본 숨김이며, 저장 시 COM 오류 코드·모듈
  정보까지만 허용하고 문서 내용 포함 문자열은 넣지 않는다.

## 7. 작업 2: 터미널 자연어화 (원안 유지)

기본 사용자 모드("작업 내역")와 상세 개발자 모드("상세 로그")로 분리,
접기·펼치기, 원안 7.4 템플릿 예시와 7.5 품질 원칙(특히 `verified=False`
검증 표현 금지, `undo_available=False` 되돌리기 표현 금지) 전부 유지.

보강 한 가지: 템플릿 문구는 기존 편집 결과 메시지의 확립된 한국어 톤
(무엇을 했는지 → 검증 여부 → 다음 행동)을 따르고, 같은 액션의 채팅
결과 문장과 진행 영역 문장이 서로 모순되지 않아야 한다.

## 8. 작업 3: 되물어보기 구조 (개정)

### 8.1 상태 일반화 (원안 유지)

`confirmation_required`(실행 승인·위험 확인)와
`clarification_required`(정보 부족·모호)를 reason으로 구분하고 UI는
기존 확인 카드를 재사용한다.

### 8.2 사유 코드와 triage 매핑 (보강)

원안 11종 사유 코드를 유지하되, 기존 failure triage 분류와의 매핑을
고정해 진단·통계를 일원화한다.

| 사유 코드 | triage 분류 |
|---|---|
| `missing_*` (target/range/destination/sort_key/filter_condition) | 사용자 정보 필요 |
| `multiple_possible_intents`, `ambiguous_reference` | 사용자 정보 필요 |
| `multiple_documents`, `multiple_sheets` | 사용자 정보 필요 |
| `context_mismatch` | 대상 변경 (기존 `target_changed` 계열) |
| `unsafe_default` | 위험 확인 (기존 confirmation 경로) |

구현 시작점: 현재 Stage5/6 분석기의 안내 예외(Stage5EditError)는 이미
"지원 예시" 문장을 담고 있다. 슬롯이 특정되는 경우(예: 합계의 대상
범위·결과 위치)부터 이 예외를 구조화 사유 + 선택지로 승격한다. 전부를
한 번에 바꾸지 않고, 승격되지 않은 경로는 기존 안내 문장을 유지한다.

### 8.3 되물어보기 반환 형식 (원안 유지)

원안의 `clarification_required` + `confirmation{reason, options[]}`
구조를 그대로 쓴다. `recommended: True` 선택지는 포커스 기본값이 된다.

### 8.4 질문 빈도 정책 (개정 — 정의 고정)

- **바로 실행**: 의도 유일 + 필수 정보 완비 + 안전 + 검증 가능 + Undo
  가능. *단, 쓰기 작업의 "실행"은 기존 계약대로 미리보기+승인을 뜻한다.*
- **추천 후 실행**: 합리적 기본값이 있으면 **기본값을 채운 미리보기를
  추천 선택지로 제시**한다. 승인 없이 실행하는 등급이 아니다. 학습된
  생략값 채움(승인 서식 선호)이 이미 이 방식이므로 같은 경로를 쓴다.
- **반드시 되물어보기**: 삭제·덮어쓰기, 후보 복수, 결과 위치 불명, Undo
  불가, 사용자 표현과 문서 상태 충돌. (원안 유지)

### 8.5 과잉 질문 방지 (원안 유지)

같은 선택 3회 반복 → "앞으로 이 방식을 먼저 쓸까요?" 확인 후에만 우선
적용. 즉시 영구 기본값 확정 금지. 기존 선호 학습 계약(3회+승인)과 동일
구조이므로 `user_preference_learning`을 재사용한다.

## 10. 작업 5: Excel 완료 기준 (전면 개정)

### 10.0 재분류 원칙

실측 기준(2026-07-19 감사 배터리 + 공식 수동 시험 문서)으로 현재
구현된 액션과 신규를 구분한다. **이번 달의 목적은 A군 안정화이고, B군은
최소 신규, C군은 동결 후 백로그다.**

### 10.1-A A군 — 기존 구현, 안정화 대상

값·수식 입력(`write_cell`), 합계·평균 입력, 서식(굵게·해제, 글자 크기,
정렬, 배경·글자색), 필터·해제, 정렬, 선택·전체 치환, 행·열 삽입, 선택
읽기, VBA 조회·수정·실행(9단계), 시트 관계·조인·워크플로(10단계).

각 액션에 10.2 완료 조건 10항목을 적용해 점검하고, 미달 항목(주로
6번 자연어 설명·7번 Undo 노출)을 이번 작업으로 채운다.

### 10.1-B B군 — 이번 달 신규 (4종만)

빈도가 높고 검증·Undo·안전 확인이 명확한 것만 추가한다.

1. **중복 제거** — 반드시 되물어보기(기준 열 확인) + 삭제 경고, 제거
   행 수 read-back, Undo 지원
2. **행·열 삭제** — 삭제 경고 + 대상 범위 명시, Undo 지원
3. **시트 생성·이름 변경** — 이름 충돌 검사, read-back 검증
4. **열 너비·행 높이 조정** — 자동 맞춤 포함, 저위험

B군도 10.2 완료 조건 전부를 만족해야 하며, 일정이 밀리면 B군을 8월
첫 주로 이월하고 A군 안정화만으로 동결을 선언할 수 있다(14절).

### 10.1-C C군 — 동결, 백로그 이동

다중 기준 정렬, 텍스트 나누기, 값·날짜·숫자 형식 통일, 자동 채우기,

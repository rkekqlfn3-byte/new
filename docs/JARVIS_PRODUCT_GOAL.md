# JARVIS 제품 Goal과 수용 기준

기준일: 2026-07-18

## North Star

> JARVIS는 사용자의 자연어와 현재 컴퓨터 문맥을 이해하고, 실제 앱을 안전하게
> 조작하며, 성공한 작업과 사용자의 반복된 교정을 학습해 갈수록 그 사람에게
> 맞는 개인용 컴퓨터 대리인이 되는 시스템이다.

핵심 철학은 다음 두 문장이다.

> 너네가 나를 배워.
>
> 그리고 너네 실수도 너네가 고쳐.

JARVIS는 단순 챗봇, 명령어 암기식 런처, 좌표 클릭 매크로, Office를 흉내 낸
가짜 편집기가 아니다. 사용자가 평소 말로 목적을 설명하면 현재 앱·문서·선택과
직전 작업을 구조적으로 파악하고, 네이티브 앱에서 검증 가능한 결과를 만들어야
한다.

## 제품 수용 기준

1. **자연어를 행동으로 변환**
   - 정해진 명령문을 외우지 않아도 대표 표현과 변형 표현을 이해한다.
   - 모호하면 추측 실행하지 않고 필요한 정보 한 가지만 묻는다.
2. **현재 문맥 이해**
   - 앱, 문서 신원, 시트·문단·슬라이드, 선택 영역, 직전 작업을 구분한다.
   - `이거`, `여기`, `방금 거`, `지난번처럼`을 검증 가능한 문맥에 연결한다.
3. **안전한 네이티브 실행**
   - COM·공식 API·UI Automation의 구조적 대상을 우선 사용한다.
   - 대상 재확인 → 위험 승인 → 실행 → 재읽기 검증 → 실패 복구 순서를 지킨다.
   - 실행이 시작됐는지 불명확한 작업은 자동으로 통째로 재실행하지 않는다.
4. **성공 작업 재사용**
   - 검증된 성공만 재사용 후보가 된다.
   - 사용자 승인 뒤 로컬 스킬로 저장하고, 유사 요청의 API 의존과 지연을 줄인다.
5. **여러 앱 업무 연결**
   - Excel 분석 결과를 Word·한글 보고서와 PowerPoint 요약으로 연결한다.
   - 단계별 산출물과 후조건을 검증하고 실패 단계부터 안전하게 재개한다.
6. **사용자 방식 학습**
   - 반복 교정과 명시적 승인을 근거로 문체·분량·숫자 형식·표현·확인 정책을
     학습한다.
   - 한 번의 표현을 성급하게 전역 기본값으로 일반화하지 않는다.
7. **실패 책임 분류와 대응**
   - 자율 재탐색 가능, 사용자 정보 필요, 기능 미구현, 구현 버그, 환경·권한 차단,
     취향 불일치를 구분한다.
   - 각 분류는 재탐색, 한 번의 질문, 개발 이슈 등록, 환경 안내 등 서로 다른
     다음 조치로 이어져야 한다.
8. **비숙련자 접근성**
   - 메뉴·수식·매크로·파일 형식을 몰라도 목적을 말하면 사용할 수 있어야 한다.
   - 메시지는 기술 용어보다 `무엇을 했는지`, `왜 멈췄는지`, `무엇을 말하면
     되는지`를 우선 보여준다.

## 2026-07-18 자율 복구 첫 범위

명시적인 앱 열기·닫기 요청에서 등록된 대상을 못 찾으면 실행 전에 한 번만
Windows `App Paths`와 시작 메뉴·바탕화면 바로가기를 제한 탐색한다.

- 발견: 중앙 실행 보안 정책을 통과한 대상만 사전에 저장하고 원래 요청을 진행한다.
- 미발견: 반복 탐색을 멈추고 앱 이름 또는 위치를 요청한다.
- 탐색 오류: 환경 문제로 분류한다.
- 모든 시도는 `phase=pre_execution`, `execution_started=false`, 대상 서명 동일,
  `retry_limit=1`을 증명하는 공통 복구 계약을 먼저 통과한다.
- 요청 동사와 대상 후보의 해시 서명이 재분석 전후 다르면 실행하지 않고
  `needs_input`으로 분류한다.
- 실행이 시작된 뒤 복구 계약을 요청하면 중복 변경을 막아 거부하고 개발자 책임의
  안전 실패로 분류한다.
- 복구 ID·서명·불리언·횟수만 진단하며 앱 이름·경로·사용자 원문은 남기지 않는다.
- 제외: Program Files 전체 재귀 검색, 실행이 시작된 작업의 통째 재실행, 위험 정책
  완화는 하지 않는다.

이 범위는 `자비스가 다시 탐색하면 해결 가능한 실패`를 실제 실행 고리로 만든 첫
단계다. 이후 복구도 같은 원칙, 즉 **실행 전임을 증명할 수 있고 대상이 그대로일
때만 1회** 허용한다.

## 2026-07-18 연결 문서 focus 복구

상태 polling이나 수동 문맥 조회는 사용자가 보고 있는 창을 바꾸지 않는다. 다만
명시적 편집 명령의 준비 시점과 사용자가 미리보기를 승인한 시점에는 아직 네이티브
변경이 시작되지 않았으므로, 연결 문서가 다른 창 뒤로 밀려 문맥 캡처가 실패하면
해당 문서 창을 한 번 활성화할 수 있다.

- `connected_document_focus` 전략도 공통 실행 전 복구 계약을 사용한다.
- 세션 ID, 문서 fingerprint, 창 handle은 기존 연결 세션에서만 가져온다.
- focus 성공을 Windows foreground 상태로 검증한 뒤 문맥을 다시 읽는다.
- 재조회한 문서 fingerprint가 요청과 같아야 미리보기 또는 승인 실행을 계속한다.
- 다른 문서가 확인되면 `target_changed`로 중단하고 현재 문서 재연결을 요청한다.
- Windows가 focus를 거부하면 `environment_blocked`로 분류하고 문서 창을 한 번
  선택하라는 단일 행동을 안내한다.
- focus 복구 중에는 셀·텍스트·선택·문서 내용을 변경하지 않는다.
- 복구 증거에는 해시·불리언·횟수만 남고 문서 경로와 내용은 저장하지 않는다.

## 2026-07-18 교정 학습 확장

편집 확인 중 사용자가 `그거 말고 좀 더 간결하게 다시 작성해줘` 또는
`취소해. 앞으로는 좀 더 친근하게 해줘`처럼 이유를 함께 말하면 확인 응답과
허용된 선호를 분리해 처리한다. 검증된 편집 뒤 `너무 길어`라고 이어서 교정한
경우에는 실제 후속 편집이 승인·실행·검증된 뒤에만 증거를 기록한다.

- 자유 문장 원문과 문서 내용은 선호 저장소에 보관하지 않는다.
- 한 번의 교정은 관찰 증거일 뿐 기본값을 바꾸지 않는다.
- 현재 미리보기 피드백은 `앞으로·항상` 같은 일반화 표현이 없으면 파일 범위다.
- 같은 값 3회와 사용자 승인이 있어야 활성 기본값이 된다.
- 학습 저장 실패는 취소·재작성·문서 검증을 방해하지 않는다.

## 2026-07-18 직접 수정 관찰 첫 범위

JARVIS가 Word·한글·PowerPoint의 선택 텍스트를 편집하고 결과 검증까지 마친 뒤,
사용자가 같은 구조적 시작점의 텍스트를 직접 명확하게 줄인 경우를
`보고서 문체: 간결하게`의 파일 범위 관찰 증거로 기록한다. 축약 때문에 선택의
끝 offset이 바뀌는 것은 정상적인 네이티브 앱 동작으로 처리한다.

- 앞선 JARVIS 작업이 텍스트 치환이고 성공·검증된 경우만 관찰한다.
- 앱과 저장 문서 fingerprint가 같고, 전후 텍스트 지문이 다를 때만 후보가 된다.
- 선택 참조가 완전히 같거나, Word의 시작 offset, PowerPoint의
  SlideID·ShapeID·텍스트 시작점, 한글의 정규화한 선택 시작 좌표가 같아야 한다.
- 기존 텍스트는 30자 이상, 수정 결과는 10자 이상이어야 하며 길이 비율이
  35~75%일 때만 명확한 축약으로 본다.
- 선택 변경, 사소한 축약, 거의 전부 삭제, Excel 변경은 오탐 방지를 위해 제외한다.
- 문서 원문·자유 교정문·텍스트 지문은 선호 저장소와 UI에 노출하지 않는다.
- 같은 관찰을 반복 조회해도 증거를 중복 계산하지 않는다.
- 증거 3회 뒤에도 후보일 뿐이며, `앞으로도 간결하게 해줘`와 같은 명시적 승인이
  있어야 실제 기본값이 된다.

이 범위는 `너네가 나를 배워`를 직접 편집 행동까지 연결한 첫 단계다. 서식 변경,
문체의 세부 의미, 선택 시작점이 이동하거나 커서로 접힌 상태는 아직 안전하게
추론하지 않는다.

## 2026-07-18 직접 수정 관찰 2차 범위 (서식·말투)

첫 범위의 축약 관찰과 같은 대상 동일성 계약(문서 fingerprint, 앱별 구조적
시작점, JARVIS 검증 편집 직후) 위에서 두 가지 관찰을 추가한다. 한 사건은
정확히 하나의 관찰로만 해석하며 우선순위는 축약 > 말투 > 서식이다.

- **말투 전환**: 텍스트 지문이 바뀌었고 길이가 기존의 50~160%인 재작성에서,
  문장 어미 기반 결정적 분류(합쇼체·해요체·해라체)가 명확한 라벨에서 다른
  명확한 라벨(격식체·친근한 문체)로 바뀐 경우만 파일 범위 문체 증거로
  기록한다. 혼합·불명 라벨과 어미 밖의 의미 변화는 해석하지 않는다. 저장되는
  값은 어미 분류 한 단어이며 문장 원문은 남기지 않는다.
- **서식 변경**: 텍스트 지문이 완전히 같고 Word·PowerPoint 문맥의 굵기,
  글자 크기(1pt 이상), 문단 정렬 중 정확히 한 가지만 바뀐 경우 해당 서식
  선호(`텍스트 강조 방식`, `글자 크기 방향`, `문단 정렬 기본값`)의 파일 범위
  증거로 기록한다. 혼합·미정 상태(native sentinel)와 두 가지 이상 동시 변경은
  해석하지 않는다. 한글은 편집 문맥에 서식 정보가 없어 지원하지 않는다.
- **승인 문구 연결**: 증거 3회 뒤 안내되는 `앞으로도 …해줘` 확인 문장은 현재
  연결 파일에 같은 값으로 대기 중인 후보가 있으면 그 파일 범위 후보의
  활성화 승인으로 해석한다. 이 연결이 없던 첫 범위에서는 안내 문구가 실제
  활성화로 이어지지 않는 공백이 있었다.
- 활성화된 서식 선호의 보고서·미리보기 자동 적용은 후속 범위다.

## 2026-07-18 커서로 접힌 선택 연구

직접 수정 후 선택이 커서로 접힌 상태를 관찰에 포함할 수 있는지 앱별로
검토했다. 결론은 세 앱 모두 현재 개인정보 경계 안에서는 증명이 부족해
구현하지 않는다.

- **Word**: `Selection.Start`만으로는 사용자가 커서를 그 위치로 옮긴 것인지
  편집 후 접힌 것인지 구분할 수 없다. 선택 없이 편집 결과 텍스트의 지문을
  만들려면 사용자가 선택하지 않은 범위를 읽어야 하며, 이는 `선택한 내용만
  읽는다`는 현재 경계를 넘는다.
- **PowerPoint**: SlideID·ShapeID는 접힌 상태에서도 유지되어 shape 수준
  동일성은 증명할 수 있다. 그러나 텍스트 변화 감지는 shape 전체 텍스트
  읽기가 필요하다. 이미 shapes 선택(kind=shapes)에서는 전체 TextFrame을
  읽고 있으므로, `shape 전체 텍스트 지문` 기반 관찰은 경계 조정 없이 도입
  가능한 후속 후보로 기록한다.
- **한글**: 접힌 커서는 `GetPos()` 좌표만 제공하고 선택이 없으면
  `GetTextFile(saveblock)`을 쓸 수 없어 텍스트 지문 자체를 만들 수 없다.

## 개발 우선순위

1. PowerPoint shape 전체 텍스트 지문 기반의 접힌 선택 관찰을 검토하고, 활성화된
   서식 선호를 보고서 생성과 편집 미리보기에 안전하게 적용한다.
2. 공통 복구 계약을 닫힌 문서·UI 대상 등 더 많은 안전한 무변경 탐색에 적용한다.
3. HWP 보고서, 다중 Excel 시트, 앱 간 산출물 검증을 확장한다.

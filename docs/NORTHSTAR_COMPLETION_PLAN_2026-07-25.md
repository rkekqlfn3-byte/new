- 선행 문서: [Goal 잔여 작업 계획서](GOAL_REMAINING_PLAN_2026-07-25.md)

## 0. 확정된 방향

1. Prototype 수용 도장을 **먼저** 찍어 기준선을 만든다.
2. 그 뒤 실사용을 먼저 하고, **거기서 나온 데이터로** North Star 확장의
   우선순위를 정한다.

## 1. North Star를 "완성"으로 만들려면 먼저 경계가 필요하다

North Star 원문은 `갈수록 그 사람에게 맞는` 시스템이다. 끝점이 정의에 없으므로
그대로는 완료 판정을 쓸 수 없다. 마스터 계획도 같은 위험을 경고한다.

그래서 이 계획서는 North Star를 **한 번에 정의하지 않는다.** 대신 측정 가능한
것부터 측정하고, 측정된 실패로 다음 범위를 확정한다.

### 1.1 자동 테스트로 잴 수 없는 것

1,000문장 배터리는 mock 실행기 기반 **해석 계층** 검증이다(`외부 AI 호출 0건,
실제 앱 실행 0건`). 그런데 North Star의 핵심은 다음 문장이다.

> 너네가 나를 배워.

`갈수록`은 시간과 반복이 들어간 정의다. 개발자가 작성한 문장을 아무리 늘려도
"이 사람에게 맞아가는가"는 측정되지 않는다. **학습 축이 8축 중 가장 낮은
이유도 학습시킬 실사용 데이터가 아직 0이기 때문이다.**

따라서 North Star 검증의 필수 인프라는 더 큰 테스트 배터리가 아니라
**실사용 계측 체제**다.

## 3. Stage 1 — Prototype 수용 도장 (3~5일)

세부 실행은 [Goal 잔여 작업 계획서](GOAL_REMAINING_PLAN_2026-07-25.md)를 따른다.
여기서는 그 문서가 다루지 않은 **차단 요소 하나**만 확정한다.

### 3.1 한글 축 처리 (필수 결정)

`accepted` 판정은 `cross_app_workflow` 축을 요구하고, 이 축의 필수 probe는
`workflow_word`, `workflow_hwp`, `workflow_both` 셋이다.

- `workflow_hwp`: 보안 모듈 부재로 `environment_blocked`.
- `workflow_both`: 현재 `passed`이지만 **2026-07-18 18:55 생성분이며 한글 보안
  모듈 사전 검사가 추가되기 전 결과**다. `both` 순서에는 `create_hwp_report`가
  포함되므로, 신선도 만료로 재실행하면 함께 실패한다.

따라서 `workflow_hwp` 하나만 제외해도 `accepted`에 도달하지 못한다.

**경로 A — 보안 모듈 설치 (권장)**

1. 한컴 공식 가이드의 파일 접근 보안 모듈을 사용자가 직접 설치·등록한다.
2. JARVIS를 다시 시작한다.
3. `workflow_hwp`와 `workflow_both` probe를 다시 만든다.
4. 코드 변경 0. 수용 기준을 낮추지 않는다. 주 용도인 한글 쪽 기능도 함께 열린다.

**경로 B — 축 재정의**

1. `cross_app_workflow`의 필수 probe에서 `workflow_hwp`를 제거하고,
   `workflow_both`를 한글이 없는 조합으로 교체한다.
2. `KNOWN_LIMITATIONS.md`에 제외 범위·사유·재개 조건을 기록한다.
3. 태그 설명에 "한글 보고서 생성 제외"를 명시한다. 무엇을 빼고 받은 도장인지
   나중에 알아볼 수 있어야 한다.

어느 경로든 자동 설치·레지스트리 변경·보안 우회는 하지 않는다.

### 3.2 Stage 1 완료 조건

- Excel 100문장 수동 시험: 중대 오대상 0, 무승인 쓰기 0
- 실앱 probe 전량 7일 이내 재생성 (사용자 Office 종료 상태에서 일괄)
- 수동 수용 3종 `passed`
- 전체 회귀 실패·오류 0, `source.dirty=false`
- `overall_status=accepted`, 종료 코드 0
- `Prototype Goal accepted` 태그와 소스 아카이브

**이 태그가 North Star 확장의 기준선이 된다.** 이후 무엇이 깨졌는지 비교할
지점이 생긴다.

## 4. Stage 2 — 실사용 계측 체제 (2~3일)

North Star로 가는 유일한 나침반이다. 지금 JARVIS는 **못 하는 요청을 안전하게
차단하고 그대로 잊는다.** 무엇을 하려다 막혔는지가 남지 않으면 확장 우선순위를
영원히 추측으로 정하게 된다.

### 4.1 개인정보 경계 재정의

기존 규칙은 유지한다. 원문·문서 내용·전체 경로는 **Git, probe 보고서, 영구
진단, 소스 아카이브에 넣지 않는다.**

새 저장소는 성격이 다르므로 별도로 정의한다.

- 위치: `%LOCALAPPDATA%\Jarvis\data\usage_journal.jsonl`
- 성격: **사용자 본인 PC의 로컬 전용 기록.** 사용자가 스스로 보려고 남기는 것
- 사용자가 언제든 열람·삭제할 수 있고, 끄는 설정을 제공한다
- Git, probe, 수용 보고서, 소스 아카이브에서 전면 제외한다
- 외부 전송·API 업로드 대상이 아니다

이 구분을 `RULEBOOK.md`에 명시한다.

### 4.2 기록 항목

| 항목 | 내용 |
|---|---|
| 요청 | 시각, 모드, 원문(로컬 전용) |
| 라우팅 | 해석된 action·app·대상 종류, 로컬/AI 경로 |
| 판정 | `executed` / `clarified` / `blocked` / `failed` / `cancelled` |
| 실패 | 6종 책임 분류, 사유 코드 |
| 안전 | 승인 요구 여부, 승인·취소, Undo 노출·사용 |
| 성능 | 소요 시간, AI 호출 수 |

### 4.3 핵심 두 가지

**(1) `unsupported_request` — 확장 우선순위 1순위 데이터**

안전 차단된 요청을 원문과 함께 로컬에 남긴다. 지금은 이게 사라지기 때문에
"사용자가 실제로 무엇을 시키고 싶어 했는가"를 알 방법이 없다.

**(2) `unlearnable_correction` — 학습 축 확대의 근거**

사용자가 교정했지만 `ALLOWED_PREFERENCES` 13종 밖이라 버려진 교정을 따로
센다. 학습 축이 35%인 이유를 숫자로 만든다.

### 4.4 주간 요약

`이번 주 어땠어` 같은 로컬 명령으로 집계를 본다. AI 호출 없이 로컬 계산만
사용한다.

- 성공 / 되물음 / 차단 / 실패 건수와 비율
- 가장 많이 막힌 요청 유형 상위 10
- 학습되지 못한 교정 상위 10
- 평균 응답 시간, AI 호출 비율

### 4.5 완료 조건

- 기록 실패가 실제 작업 결과를 바꾸지 않는다
- 끄기 설정이 동작하고, 끈 상태에서 아무것도 기록하지 않는다
- Git·probe·아카이브에 저널이 섞이지 않는다(검증 테스트 포함)
- 기존 회귀 실패·오류 0

## 5. Stage 3 — 실사용 (2~4주)

사용자가 평소 업무를 JARVIS로 한다. 주 용도인 한글 문서 자연어 편집을 중심에
둔다. 이 기간에는 **기능을 늘리지 않는다.** 늘리면 무엇 때문에 좋아졌는지
구분이 안 된다.

예외적으로 즉시 고치는 것은 P0뿐이다.

- 승인 없는 쓰기·삭제·덮어쓰기
- 다른 문서·시트·선택 대상 실행
- 검증 실패를 성공으로 표시
- Undo 가능 여부의 거짓 표시
- 사용자 문서 내용·경로·API 키 유출

주 1회 요약을 확인하고, 실패 분류가 `bug`인 항목만 별도로 처리한다.

## 6. Stage 4 — 데이터 기반 확장

### 6.1 착수 규칙

추측으로 만들지 않는다. 다음 조건을 넘은 항목만 개발 후보가 된다.

| 신호 | 임계값 | 결과 |
|---|---|---|
| 같은 유형의 미지원 요청 | 4주간 10회 이상 | 기능 확장 후보 |
| 학습되지 못한 같은 축 교정 | 5회 이상 | 학습 축 확대 후보 |
| 같은 지점의 되물어보기 | 10회 이상 | 문맥·기본값 개선 후보 |
| 실패 분류 `bug` | 1회 | 즉시 수정 |
| 실행 후 실패로 수동 복구 필요 | 3회 이상 | 자율 복구 확장 후보 |

### 6.2 확장 후보 목록 (실사용이 우선순위를 정한다)

현재 43%에 해당하는 범위다. **순서는 Stage 3 데이터가 정한다.**

| 축 | 확장 내용 | 규모 |
|---|---|---|
| 학습 | `ALLOWED_PREFERENCES` 확대, 관찰 대상 확대, 자유 문장 의미의 제한적 학습 | 대 |
| 재사용 | 사용자가 허용 단계를 조합하는 승인형 레시피 편집기, 새 산출물별 검증기 | 대 |
| 앱 연결 | 임의 앱 조합, 사용자 정의 후조건 | 대 |
| 자연어 | 미등록 조합의 AI 계획 → 허용 단계 검증 → 승인 실행 | 중 |
| 복구 | 실행 후 보상 트랜잭션, 앱 재실행이 필요한 복구 | 중 |
| 문맥 | 세션을 넘는 장기 대화 문맥 | 중 |
| 네이티브 | 앱별 작업 추가 (Excel B군 4종 포함) | 소~중 |
| 접근성 | 음성 중심 UI | 중 |

전체를 다 하면 지금까지 만든 양과 비슷하거나 크다. **수 주가 아니라 수 개월
단위다.** 그래서 데이터로 잘라내는 것이 핵심이다.

### 6.3 확장 중 유지할 계약

확장이 안전 계약을 무너뜨리면 North Star가 아니라 퇴보다. 다음은 범위가
넓어져도 그대로 유지한다.

- 미리보기 → 승인 → 대상 재확인 → 실행 → read-back
- 모호하면 추측 실행하지 않고 필요한 정보 하나만 질문
- 검증된 성공만 재사용 후보
- 3회 증거 + 명시적 승인 없이 기본값 변경 없음
- 실행이 시작된 작업의 통째 재실행 없음
- 각 확장마다 Prototype 게이트 재통과

## 7. 전체 일정

```text
Stage 1  Prototype 도장            3~5일
Stage 2  실사용 계측 체제          2~3일
Stage 3  실사용                    2~4주   ← 기능 동결
Stage 4  데이터 기반 확장          수 개월 (데이터가 범위를 자름)
```

Stage 1~2는 약 1주, Stage 3은 대기가 아니라 **측정 기간**이다.

## 8. North Star 완료를 어떻게 판정할 것인가

Stage 3 데이터가 쌓이면 그때 다음을 숫자로 고정한다. 지금은 고정하지 않는다.

- 주간 미지원 요청 비율이 몇 % 아래인가
- 학습된 선호가 실제로 몇 개 활성화되었고, 사용자가 몇 개를 유지했는가
- 같은 교정을 반복하지 않게 되었는가 (`갈수록`의 유일한 실측 지표)
- 사용자가 실패했을 때 스스로 복구한 비율

**마지막 항목이 North Star의 진짜 시험이다.** 자동 배터리로는 영원히 잴 수
없고, 실사용 기록으로만 잴 수 있다.
